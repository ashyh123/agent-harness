# 关闭独立模型核对：三组真实对照

日期：2026-10-10。结论：**本次不能证明关闭核对能保持完成效果并稳定节省预算，因此保留为可选模式，不改变默认实现。**

## 同批次完整结果

4项任务 × 3次重复 × 3组 = 36次真实DeepSeek执行。完成率采用共同的外部严格验收，再人工检查博客答案；框架自己的通过标志不作为最终完成证据。所有失败运行的消耗均计入。

| 模式 | 人工复核后严格完成 | 自动通过 | 总 tokens | 平均耗时 | 模型请求 / 核对请求 |
|---|---:|---:|---:|---:|---:|
| 原 Harness（有相同检索工具） | 9/12（75.0%） | 9/12 | 205,202 | 7.193 秒 | 55 / 0 |
| LangGraph：程序验收，关闭核对 | 8/12（66.7%） | 8/12 | 256,328 | 8.273 秒 | 67 / 0 |
| LangGraph：程序验收＋模型核对 | 9/12（75.0%） | 10/12 | 261,027 | 8.994 秒 | 73 / 5 |

关闭核对相对开启核对：总tokens下降1.80%，平均耗时下降8.02%，但严格完成率从9/12降至8/12。样本很小，不是统计显著性或等效性结论。

## 关键失败与人工核对

- 程序验收组：第一轮evals博客10次外层模型请求、16次工具调用，46,278 tokens后触发请求上限；读取证据/修正未完成，而非模型服务故障。
- 三轮managed博客程序验收均返回了答案，但有引文缺少`getSession`或`getEvents`，不足以支撑对应事实；“真实子串”不等于“支持答案”。第二轮还把wake/getSession顺序颠倒。
- 模型核对组：第二轮managed答案自动通过，却把`getSession`写在`wake`之前，人工复核否决。原文先wake重启新Harness，再getSession取回事件日志。独立模型核对不是正确性保证。
- 模型核对组：第三轮managed在修正阶段耗尽10次外层请求，36,143 tokens，没有交付已验收答案。
- 原Harness三次managed均因引文超过100字符而未达严格格式要求；这不等于完全没理解文章。本实验同时要求事实与引用满足指定交付格式。

人工复核：核对所有博客最终答案的事实、限定条件与引用含义；所有自动通过的evals答案未发现额外语义错误。仅对“自动通过但人工否决”的结果扣分，未放宽引文支持/长度/JSON规则。原始人工备注见批次`manual-review.json`。

## 控制与计量

- 模型deepseek-flash，temperature=0，thinking关闭，SDK自动重试关闭。
- 三组相同任务、Skill、快照、工具schema、上下文策略与预算。每项任务每次重复的首个请求body（model/messages/tools/temperature/max_tokens/thinking）哈希一致：12/12三元组。第二轮、第三轮轮换执行顺序，每组先执行一次。
- 预算：外层请求10次、全部模型请求16次、工具16次、180秒、每次模型输出1024 tokens。摘要/核对使用原共享预算，无额外隐藏额度。这里未设总token硬上限。
- 上下文仍是legacy：trigger=12000、target=8500、max_input=64000、summary_output=1024、keep_recent=2000；检索均为SQLite FTS5/BM25，回读固定真实网页快照，不测网络抓取可靠性。
- 博客工具：read_saved_webpage/search_saved_webpage；数据工具：read_data/query_data/calculate，组间一致。原Harness也获得检索工具，因此不是与没有检索的旧版本比较。
- tokens是模型响应usage.prompt_tokens+completion_tokens总和，包含摘要、核对、失败运行中的已报告用量。缓存tokens仍算tokens；未折算人民币，不把token比例视为账单节省比例。
- 耗时是每次独立运行的本地计时，包含启动、工具、模型、核对、修正与记录，不含组间等待；表中是每次运行平均值，不是总批次墙钟耗时。
- 外部验收采用严格JSON、实际回读引文、标准事实、引文长度/支持性、数据数值与工具轨迹。运行时validator没有标准答案。离线人工复核不增加模型请求。

## 排除的基础设施故障批次

第一次36次尝试保存在`reports/langgraph-runs/evidence-ablation-r8j7w6`。记录出现29次TypeError、2次TimeoutError，且有超过本地180秒的异常墙钟耗时；没有证据将原因确定为余额或某个服务商问题。该批不纳入策略优劣比较，也没有把失败的零tokens算成节省。随后独立健康检查HTTP200（40 tokens，另计），重新跑完整36次。本报告只比较第二个完整批次；第二批未出现模型连接/超时错误，有2次正常预算终止。

这些排除不代表第一次尝试没有消耗费用；所有原始记录保留，报告没有将两批或此前24次结果混算。

## 实现与复现

`readingReview: 'structural'`只改变validate通过后的边：直接finish，不进入critic。来源、问题覆盖、JSON、逐字引文和长度验证及失败修正保留；默认semantic不变。记录保存reading_review，可检查graph_nodes及reading_critic事件。单元测试覆盖最后一次请求直接交付、缺引文仍修正、以及真实引文不能证明错误数字；143/143测试通过，TypeScript类型检查通过。

在vercel_agent目录：

```sh
npm run verify:evidence-reading -- 3 --ablation
npm run harness:langgraph -- --no-critic --contract examples/blog-questions.json webpage-reader '根据约定回答问题'
```

原始完整批次：`reports/langgraph-runs/evidence-ablation-4Cm9Uk`。可机读摘要：[evidence-ablation-summary.json](evidence-ablation-summary.json)。此前两组实验保持独立：[evidence-reading-validation.md](evidence-reading-validation.md)。

本批数据支持继续保留开关，不支持全面淘汰模型核对，也不支持把核对当作可信验收。要提高这两篇博客的严格完成率，下一步应围绕引文是否实际支持具体回答和无效修正循环处理，而不是仅增减一次核对请求。
