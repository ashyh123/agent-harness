# 单篇博客的按需阅读验收

日期：2026-10-09。结论：**此任务没有证据支持淘汰原上下文策略或切换新策略为默认。** 原策略在原执行预算与两倍执行预算下均通过3/3；新策略分别通过2/3、3/3。默认策略仍为 `legacy`，生产预算及12000/8500容量设置未改。

## 任务与通过标准

按照用户确认的范围：单篇厂商技术博客、三个固定事实问题、回答及原文证据可核查；允许按需阅读，不要求全文覆盖。

材料为已有的 [Anthropic 评测博客](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) text快照，38429个Unicode码点。三个问题及人工核对要点：

1. 初期评测应从多少个任务起步，任务来自哪里？20–50个简单任务，来自真实失败；这是初期建议。
2. `pass^k` 衡量全部k次成功还是至少一次？全部k次成功的概率。
3. 航班预订示例的成功依据是什么？环境SQL数据库中实际存在预订，Agent口头声称完成不足以验收。

每次运行必须三问都答对，各有12–100字符的逐字连续英文引文；引文必须出现在本轮真实工具读取范围内，并支持对应事实。来源URL正确，提取完整性仍标为未验证。保留影响答案的条件及来源限定，不可凭记忆补证据。程序检查后逐次人工复核语义与否定关系。本轮以每档三次全部通过作为局部门槛，不将3/3解释为总体可靠率已达100%。

覆盖率只作为诊断。没有将旧全文实验重新打分，也没有把全文阅读的失败改判为成功；这是新的任务提示词、输出格式和验收目标，不能直接比较两轮通过率。

## 固定条件

组内只切换 `legacy` / `working_memory`，其余条件相同：`deepseek-flash`、原有八个工具与相同Schema、同一Skill、逐字相同任务、同一快照、temperature=0。不给模型标准答案、证据偏移或额外检索工具。每档重复三次，轮换提交顺序。

| 上限 | 原执行预算 | 两倍执行预算 |
| --- | ---: | ---: |
| 外层模型请求（包含摘要） | 5 | 10 |
| 全部模型请求 | 8 | 16 |
| 工具尝试 | 8 | 16 |
| 步骤启动时间预算 | 90秒 | 180秒 |
| 单次正常输出 | 512 tokens | 512 tokens |
| 单次摘要输出 | 最多1024 tokens | 最多1024 tokens |

双方共同沿用先前有效对照的20000触发、14000目标、本地安全输入64000（均为估算），近期预算2000。**“原预算”指原请求、工具、耗时配额，不代表生产入口的12000/8500容量配置。** 公共容量配置不是新策略的独有收益。此次两倍档只增加执行配额，不扩大回答长度；与之前同时扩大输出上限的预算实验不同。

真实工具从已有持久快照回读；没有重新下载文章、调用外部搜索、保存到Obsidian或改变生产工具。摘要和回查均计入预算；失败运行保留。

## 结果

| 指标 | 原预算旧策略 | 原预算新策略 | 两倍预算旧策略 | 两倍预算新策略 |
| --- | ---: | ---: | ---: | ---: |
| 三问及证据全部通过 | 3/3 | 2/3 | 3/3 | 3/3 |
| 答案和证据均合格的事实 | 9/9 | 8/9 | 9/9 | 9/9 |
| 模型请求总数 | 14 | 13 | 14 | 14 |
| 工具尝试总数 | 10 | 10 | 9 | 9 |
| 累计计费tokens | 85993 | 81184 | 88181 | 89370 |
| 成功压缩次数 | 3 | 3 | 3 | 3 |

12次运行都完成一次压缩，没有预算耗尽或输出截断。每次实际模型请求为4–5次、工具3–4次，耗时约5.6–7.7秒；两倍档没有用到新增请求配额。因此不能把新策略2/3变成3/3归因于扩大预算，模型波动及读取选择差异同样可能解释。

新策略两倍档tokens增加约1.35%，通过数和请求数相同，未达到预先采用规则的10%节省。原预算新策略tokens较少，但完成度下降，不能当作等质量效率提升。

实际读取24000或30000字符，约覆盖62.5%或78.1%。所有三问的关键材料都位于这些已读范围，因此合格回答无需补齐剩余文章。模型仍主要顺序读取；现有回读工具不能在快照内按关键词定位，允许按需阅读不等于已经具有高效检索能力。

## 唯一失败与代码风险

原预算新策略第一次：三个答案都正确，预订示例引用也确实存在，但100字符的引文停在转折前，没有包含数据库实际状态。它只能证明模型读到预订示例，不能支持成功判定这个答案，所以保持未通过，不降低验收标准。

`working_context.ts` 当前会先验证长引文存在，再保留前100字符作为定位片段。这样的片段可能留下例子的铺垫，丢掉后面的关键条件。此次错误与这一风险吻合；运行记录没有保存摘要正文，无法确定是摘要提取、截取定位片段还是最终回答选句出了问题，不能据此断言根因已被完全定位。

下一步修复应使“定位片段”和“支持答案的证据”分别承担职责，并在需要精确引用时回查足够上下文；不能仅以字符串存在作为事实得到支持的证明。本轮为保持候选版本一致，未在看到结果后修改策略或重跑挑选成功记录。

## 决策与限制

原策略在这个受控配置与指定任务上达到本轮局部门槛，可以继续作为方案。它在旧的全文任务中未达标的记录仍成立；不能推广为旧策略适合所有长文。

新策略在原预算下未满足全部重复通过；两倍档也没有胜过原策略。因此不切换默认。结构化状态和近期窗口仍是可选实验能力，本轮不支持放弃这些方向。全部压缩记录的近期完整组保留量均为0，因此没有验证近期窗口的独立收益。

只有一篇既有快照、三个问题、三次重复。这不是新的留出任务，也不证明实时网页提取、陌生文章或任意问题的能力。正常入口的12000/8500容量未在此次真实对照中验证，不应将本表直接当作默认入口的保证。

## 修改与复现

- `vercel_agent/targeted_reading.ts`：新的按问题提示词和评分；复用原事实、引文及读取区间检查，取消全文覆盖门槛。旧全文评分器保留。
- `vercel_agent/verify_targeted_context.ts`：经由真实MinimalHarness配对执行两个预算档，记录清单、配置哈希、回答、范围、用量与局部资格。
- `vercel_agent/tests/targeted_reading.test.ts`：验证相关片段足够时通过；未读证据、遗漏来源限定、改写引文、错误URL、重复问题或假称提取完整均被拒绝。
- `vercel_agent/package.json`：增加 `verify:targeted-context` 入口。

```sh
cd vercel_agent
npm run verify:targeted-context -- 3
```

命令会消耗真实模型用量，需要本机已有的固定快照。不会覆盖旧实验。此次类型检查、全部70项TypeScript测试和差异空白检查通过。
