# Harness 上下文策略对照

日期：2026-10-09。结论：新策略已接入为 `working_memory` 可选项，**未切换默认**。两倍预算的开发集有明显改善，但原预算的留出集退步，不满足预先制定的采用条件。现有默认仍为 `legacy`，执行预算和12000/8500的压缩阈值/目标均未改。

后续用户将核心目标明确为单篇博客、三个固定问题、可核对证据，允许按需阅读。[新的12次按需阅读验收](targeted-context-validation.md)中，旧策略两档均3/3，新策略原执行预算2/3、两倍档3/3。任务与输出目标改变，不能直接与本报告的全文通过率比较；本报告原结果和评分保留。

## 实现

- `vercel_agent/context.ts`：保留原策略，配置策略开关及近期窗口预算，来源记录兼容两种内部状态。
- `vercel_agent/working_context.ts`：保留近期完整调用/结果组，整理较旧消息；结构化状态包含目标、约束、事实、来源调用ID、连续引文、已完成事项、缺口和下一步。旧事实及约束在重复压缩时合并保护，容量不足明确停止。
- `vercel_agent/agent.ts`：通过现有 `prepareStep` 应用策略；使用 SDK 现成 `Output.json()` 生成状态，压缩仍计入原有共享请求及耗时预算。无效格式不提交历史；引文不匹配时降为待核实猜测，允许继续回查。引文有效仅证明该片段存在，不能自动证明事实解释正确。
- `vercel_agent/harness.ts`：运行清单记录策略、容量和温度；测试可重放工具返回，生产工具库不变。
- `vercel_agent/context_eval.ts`：独立采用判定；`verify_context_strategy.ts` 真正经由 `MinimalHarness` 运行两组任务。

近期窗口按估算tokens和剩余容量选择后缀；不拆散一批调用及其结果，不保留孤立ID。单组过大则不保留该组。引文先完整验证，再保留最多100字符的连续定位片段，长片段标记 `quote_excerpted`；完整原文仍由原工具回查。本次没有增加工具、切换模型、接入向量数据库或修改SDK核心循环。

## 固定条件与评分

每一对运行使用同一 `deepseek-flash` 模型、原有全部8个工具、相同工具Schema、逐字相同的任务及评测Skill、temperature=0、相同公共网页快照。工具参数、最终输出要求及评分器一致。各组每项任务重复3次，轮换提交顺序。真实模型仍有波动，temperature=0不保证逐次完全相同。

| 限额 | 开发集两组 | 留出集两组 |
| --- | ---: | ---: |
| 外层模型请求 | 10 | 5 |
| 全部模型请求（含摘要/内部模型） | 16 | 8 |
| 工具尝试 | 16 | 8 |
| 步骤启动耗时预算 | 180秒 | 90秒 |
| 正常单次输出 | 1024 tokens | 512 tokens |
| 摘要单次输出上限 | 1024 tokens | 1024 tokens |
| 压缩触发 / 目标容量 | 20000 / 14000（估算） | 20000 / 14000（估算） |
| 本地安全输入上限 | 64000（估算） | 64000（估算） |

两组只切换上下文策略，其余限额相同。开发集沿用已有两倍预算配置；留出集使用当前正常入口的原始执行预算。不同预算组之间不做策略因果比较。

最初直接使用原12000/8500容量配置，长文任务的任务、指令、工具Schema及来源索引最低占用就达8757–9099（估算），超过8500目标。两种策略都在摘要请求发出前停止。此组不能检验压缩效果，因此保留原始结果，随后**同时**调整两组触发/目标为20000/14000；没有扩大两组请求、工具、输出或安全输入上限。该公共容量调整与新策略的作用分开解释，不能把所有改善归因于新策略。

阅读通过要求：实际工具返回范围覆盖整份提取快照、预设事实正确、短引文在实际读到的内容中连续逐字出现且支持核对点、引文长度符合要求、来源正确、必需输出字段齐全。计算通过要求：真实计算工具结果及最终JSON数值正确。运行结束或答案听起来合理都不算通过。

采用规则在首次运行前确定：完整配对、硬预算合规、双方实际发生压缩、各任务类别通过数和有证据的事实数不下降；总通过数提高，或通过数相同且tokens至少减少10%、请求不增加。开发集用于修复实现，留出集不用于调参。最终采用还要求留出集不退步。
