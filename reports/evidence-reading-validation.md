# 按问题检索、程序验收与独立模型核对：真实对照

2026-10-10，正式24次真实DeepSeek运行，每题每组3次。**同口径自动严格验收8/12→11/12，人工复核含附加事实错误后8/12→10/12；总tokens增加50.26%，平均耗时增加33.04%。** 结果说明验收修正改善了输出合规，但没有证明语义核对可靠或更省。

## 实现

- `search_saved_webpage` 使用Python自带sqlite3的FTS5/BM25，在完整text快照上临时建1000字符、150重叠的块索引；返回最多5个位置与250字符预览。严格转义查询词，不联网、不需embedding或新密钥。必须read_saved_webpage回读后才可引用。它是本地关键词检索增强，不是语义向量RAG，中文问题通常需要模型选择英文原文关键词。
- LangGraph直接编排model/tools，并新增validate/critic节点。readingContract只含来源、文档ID、用户问题与引文长度；没有答案正则、标准答案或预设事实。未提供contract时保留上一版循环。
- 程序核对完整JSON、问题ID、来源、范围标识、引文长度、逐字引文是否在实际text回读结果中。可合并连续区间，不能用未读空洞补全。检索预览不算实际回读证据。
- 独立核对使用同一个deepseek-flash，通过独立上下文只看问题、候选答案、引文和实际已读原文附近的有限上下文。无工具、无执行历史、无测试答案；supported/unsupported/insufficient逐问判定。
- 失败反馈进入原循环继续检索/修改，不重新start，不清零预算，不重跑成功工具。核对、摘要与重试同样计入模型请求与耗时；无法验收时不交付候选答案。输出截断后的通知与JSON答案分开，不破坏结构化输出。
- 新检索结果的压缩索引只保留文档、查询与命中位置，省略预览；原文仍在固定快照中。

## 正式对照控制

|条件|两组共同配置|
|---|---|
|模型|deepseek-flash；temperature=0；thinking disabled；网络重试0|
|预算|10外层模型请求、16总模型请求、16工具尝试、180秒、每次输出1024tokens|
|上下文|legacy；trigger12000、target8500、max_input64000、summary输出1024、recent2000|
|博客工具|read_saved_webpage、search_saved_webpage，描述/schema/顺序相同|
|数据工具|calculate、read_data、query_data，描述/schema/顺序相同|
|任务|两份固定博客快照按问题回答；同一JSON/CSV内联数据|
|运行|每题每组3次，交替先后顺序，每次独立上下文|

原执行器是Vercel ToolLoopAgent，实验组是LangGraph+验收修正。两组都获得新检索工具、相同按任务开放的工具范围和检索索引压缩规则，因此不能把FTS检索改善归功于LangGraph或独立核对。12对首请求规范化哈希全部相同。核对的独立上下文来自真实已读片段，不包含评测的answerPattern/sourcePattern。

tokens采用供应商真实usage（prompt+completion，含核对、摘要、失败请求的已返回usage）；没有总token硬额度，预算上限为请求次数等。耗时是完整本机墙钟时间，包含桥接、网络、工具和日志，不是框架CPU开销；API延迟、缓存、模型输出存在波动，3次不能证明显著性。

本轮按用户选择A测试定向问题核对，Managed Agents题不再要求全文总结。两组本轮任务文本完全一致，但不要把本轮通过率直接与上一轮全文任务的0/3作因果比较。

## 三种验收口径保持透明

原targetedChecks的parseAnswer允许从附加说明/Markdown代码块中抽出JSON，按该既有口径原组9/12、新组11/12。本轮提示始终要求“最终只输出JSON”，所以离线对两组同时补充完整JSON与共同程序验收，得到8/12和11/12。原组额外失败的一次是先输出英文说明再给JSON代码块，事实没有答错。原comparison.json不覆盖，review.json保存共同复核；新评测入口已统一这一评分逻辑。没有事后改问题、预算、标准事实或引文上限。

**人工复核发现核对器漏判：** 新组Managed Agents第2次写“用getSession(id)取回事件日志，再用wake(sessionId)重启新harness”。已读原文是先用wake重启新harness，再getSession恢复日志。预设接口正则与独立模型均放行了这个附加步骤的顺序错误。若严格要求整个答案都正确，该次应失败，因此保守人工通过数是10/12。这也是为什么不把自动11/12当作语义正确性保证。所有博客答案均已逐份复核，数据任务以精确结果和实际工具证据校验。

## 实际修正与失败

- 长博客38,429字符：两组使用完整快照检索，均找到了第20,387字符后的20–50任务建议。原组3次事实正确，其中一次输出格式不合规。新组3次通过，经历2次程序否决修正；这主要证明检索定位和输出验收，而不是独立核对消除了事实幻觉。
- Managed Agents：原组3次事实接口/TTFT数字正确但引文过长；新组2次自动通过，其中一次有上述额外语义顺序错误。另一次连续5次没有修正超过100字符的引文，最终10次模型请求耗尽，本轮answer=null，保留日志。不是搜索找不到，也不是无条件自动成功。
- 新组共5次独立核对请求，实际全部放行；真实运行没有观察到语义核对否决后成功纠错。离线HTTP测试证明该分支会修正并计预算，但不能据此声称真实语义核对效果优秀。
- JSON/CSV精确结果保持：JSON筛选求和300、均值150，CSV逗号/双引号正确转义；空值报错修正后求和60、均值20，保留前导零与字段内换行。

## 预试与边界

正式24轮之前有两轮预试：evidence-ghrMMl已保存7个结果，evidence-yTnu0S已保存10个结果，另有中断时未收尾的目录。它们因接入容量问题被明确中止，不与正式同配置24轮混算：初版检索预览进入来源索引造成容量失败；修正索引后，6个通用工具schema及多次回读索引仍挤压8500软目标。最终两组共同收窄工具范围，未扩大任何预算、输出额度或上下文阈值。预试原始记录仍保留，17个已收尾预试任务也实际产生了API用量；正文tokens仅对应正式24次，不是本次开发的全部账单。

当前关键词FTS不保证召回，独立核对使用同模型也可能相关性犯错；任务规模只有两篇博客、固定问题。未启用向量库、子Agent、人工交付审批或模型步checkpointer。不自动承诺全文覆盖，未写入Obsidian。

## 使用与建议

保留原Harness为默认；新策略作为带readingContract的定向阅读入口。优先使用免费快照检索和程序验收；语义核对暂为显式启用的质量检查，需要更多不同文章/问题的留出测试。下一步应改善具体格式反馈与重复无效修正的检测，并专门测试顺序、否定、单位和条件错误；不要仅根据自动通过率替换全部任务执行器。

在vercel_agent执行：

```sh
npm run harness:langgraph -- --contract examples/blog-questions.json webpage-reader "根据约定回答问题"
npm run verify:evidence-reading -- 3
node --import tsx review_evidence_reading.ts ../reports/langgraph-runs/evidence-lLMzCH
npm run typecheck
npm test
```

例子依赖本机已有快照；JSON只有问题，不含答案。换文章时先读取网页取得document_id，再提供自己的来源和问题约定。CLI只开放两种阅读工具，保留默认请求预算，不自动获得本轮2倍实验额度。
