# 手写 Loop 与 Vercel AI SDK Loop 对比

2026-10-07，手写基线提交 `1c574be`。保留原 `agent.py`，新增 TypeScript `ToolLoopAgent` 入口，共用 `tools.py`、Pydantic 参数模型和工具实现。

结论：本次 SDK 版能完成与原版相同的主要操作，调用次数相同，Token 接近；SDK 减少的是通用循环的维护工作，不能从这些样本推导出模型更聪明、答案更准确或费用更低。预算、截断恢复、失败回滚和事实验收仍需应用负责。

## 实验条件

- 同一个 DeepSeek 主模型 `deepseek-flash`，同一密钥；视觉工具复用原客户端和视觉配置。
- 同一系统提示词、四个工具、工具定义顺序、问题文本。
- 5 次外层请求、8 次模型总请求、8 次工具尝试、90 秒预算、512 token 主输出上限；模型失败重试均为 0。
- 网页真实抓取到 8256 字符正文，`truncated=false`；DuckDuckGo 真实返回 2 条搜索结果。抓取结果对两版重放，避免外部资料随请求变化。重放工具不重新搜索/下载，工具耗时不代表实时网络性能，也不验证模型改换关键词后的搜索效果。
- 计算和图片工具正常执行；同一合成图片 2024=120、2025=150，预期增长 25%。视觉调用也计入模型请求总数和 Token。
- 两版先后顺序按场景交替，各场景各跑一次，未固定随机种子。Token 使用 API 原始返回总数，不换算成费用，未控制缓存命中。

原始问题、完整答案、工具参数/结果、模型用量、SDK 步骤和抓取资料见 [JSON 执行记录](vercel-sdk-comparison.json)。

五组均返回答案，主运行错误均为空。SDK 总 Token 少 130，约 0.51%；差异非常小，包含模型输出和消息序列化差异，不能证明 SDK 更省。时间是每组从开始运行到返回记录的端到端耗时，包含各自的桥接开销，且只有一次采样，不据此判断性能优劣。

两版网页任务都发生一次 `finish_reason=length`，再使用相同的精简策略成功返回。3 次模型请求分别是“申请读网页 → 初次回答截断 → 精简重试”，没有重新读取网页。

两版图片任务均执行 `analyze_image → calculate → calculate`；5 次模型请求包含 4 次外层请求和 1 次视觉请求。得到 150−120=30、30÷120=0.25，再以百分比表达为 25%。

## 人工验收

| 场景 | 验收标准 | 手写版 | SDK 版 |
| --- | --- | --- | --- |
| 乘法 | 实际执行 calculate，答案 56088 | 通过 | 通过 |
| 除零 | 实际收到 division_by_zero，解释失败，不编造数值 | 通过 | 通过 |
| 搜索 | 使用搜索工具，引用工具返回的 URL | 通过 | 通过 |
| 图表 | 识别 120、150，调用计算工具，答案 25% | 通过 | 通过 |
| 网页 | 使用给定来源，回答两个问题，覆盖主要主题、不误述原文范围 | 部分通过，覆盖不足 | 部分通过，范围误述 |

网页原文主线是持久化动机 → 古老的存储需求与存取一体 → 内存/文件/数据库/云对象存储四种选择 → 内存退出丢失 → JSON 文件实现历史保存与读取（UTC、接口）→ 全量读写、并发、半写损坏四处问题 → 数据库事务、后续会话与认证。数据库是铺垫，原文没有展开具体数据库产品或完整技术发展史。

手写版正确解释存储先于数据库、存取关系、四种存储、事务与后续会话，但精简答案只概括“文件方案/天花板”，没有说明 UTC、历史接口以及四处问题的具体内容；对“网页讲了什么”的覆盖偏弱。

SDK 版列出了 JSON、UTC、历史接口和四处文件隐患，覆盖较完整；但把存储历史描述为“只有一句人文概述”。原文有专门的“存储：一件很古老的事”小节，包含存储先于数据库、古老记录方式、文字可能源于记账，以及存取与检索关系的多段讲解。“没有完整技术发展史”成立，“只有一句”不准确。两版都引用了实际返回的来源 URL。

因此本次不能把“返回完整答案”记作网页任务完全通过。精简成功解决了输出被截断的问题，覆盖与事实仍须人工检查。

## 工程差异

| 部分 | 手写版 | SDK 版 |
| --- | --- | --- |
| 循环与消息 | 自己读 tool_calls、执行、填 tool_call_id、继续请求 | ToolLoopAgent 自动调度并构造 SDK 消息 |
| 工具声明 | Python Tool + Pydantic 生成 schema | 导出同一 schema，包装成 SDK tool；未复制业务实现 |
| 无效参数/未知工具 | execute_tool 返回原工具错误 | SDK 执行前校验，产生 SDK 工具错误；两版都计入预算 |
| 普通工具业务失败 | 作为数据交回模型 | 复用相同工具错误数据，SDK 继续请求模型 |
| 预算失败 | 直接抛出并停止 | SDK 可能将执行异常当作工具结果，需要额外终止检查 |
| 512 token 截断恢复 | 应用实现 | 仍是应用实现，SDK 本身没有替代该策略 |
| 视觉内部请求统计 | RunContext | 桥接使用同一个 RunContext，额外模型请求不能漏计 |
| 工具并发 | 顺序执行 | SDK 可以并行调度，但本项目桥接顺序执行 |
| 正确性判定 | 根据工具证据验收 | 同样需要验收，循环结束不等于任务正确完成 |

这次迁移出现过一个离线测试失败：工具预算超限后，在 SDK 步骤观察回调里抛异常没有终止生成，导致试图继续下一次模型请求。查阅安装版本源码确认观察回调会吞掉异常。现在把失败记录到状态，并由 `prepareStep`、HTTP 请求前以及生成结束后的检查强制终止，相关测试已通过。

SDK 的工具异常转为错误结果通常有助于模型纠正操作，但“预算已耗尽”属于整个任务必须停止的错误，不能与除零这种可以解释的业务错误混为一类。这是引入 SDK 后仍需要理解执行语义的具体例子。

这里新增了 TypeScript ↔ Python 子进程桥接，因此整个新入口代码量并没有变少。它用于学习时控制工具变量；如果以后项目和工具都使用 TypeScript，可以直接用函数作为 SDK 的 execute，无需这层桥接。

## 验证与使用

原 Python 25 项测试、SDK 13 项离线测试通过；`npm run typecheck` 通过。离线测试使用真实 SDK 与真实工具桥接，只模拟 HTTP 模型响应，覆盖 ID 匹配、参数/未知工具、除零、多工具预算、视觉共享预算、输出恢复、截断参数不执行、外层上限、HTTP 不重试与历史提交。

从项目根目录：

```sh
cd vercel_agent
npm run chat
```

复验五组实测：`npm run compare`。会消耗模型用量并覆盖 JSON 记录；本 Markdown 是本次运行的人工验收，重新运行后需要相应更新，不能把旧结论直接套在新答案上。

下一步适合围绕一个具体任务加入验收标准、再改善失败处理或工具体验。保留手写版作为学习参照，以 SDK 版承接后续功能即可；当前证据不支持为了“成熟”而继续扩建通用框架。
