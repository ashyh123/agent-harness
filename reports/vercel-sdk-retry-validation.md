# SDK 模型请求重试验证

2026-10-07，`ai@7.0.130`，`@ai-sdk/deepseek@3.0.61`。

使用真实 SDK、真实 Python 桥接及计算工具，只模拟模型 HTTP 返回；不加载 `.env`，不访问 DeepSeek，不消耗真实模型用量。

核心场景：第一次模型请求返回三个计算调用（1+2、2×4、10−3），Python 分别得到 3、8、7；下一次模型请求返回 HTTP 503；SDK 原生重试后得到模拟最终回答。

## 验收结果

| 场景 | 实际 HTTP 请求尝试 | 工具执行 | 最终行为 |
| --- | ---: | ---: | --- |
| 第二次请求 503，允许重试一次，重试成功 | 3 | 3 | 返回模拟答案，提交本轮历史 |
| 同样出现 503，但模型总预算只有 2 | 2 | 3 | 拦住重试的 HTTP 调用，报告模型预算超限，不提交本轮历史 |
| 第二次请求及其重试均为 503 | 3 | 3 | 重试次数耗尽，报告失败，不提交本轮历史 |
| 第二次请求抛本地 TimeoutError | 2 | 3 | 不触发 SDK 原生重试，报告失败 |

成功重试场景直接断言失败请求与重试请求的完整请求体相等。两者均包含三个工具结果及原调用 ID `a`、`b`、`c`；工具事件总数只有三个，因此验证了既复用结果，也没有重新执行工具。

该场景的 SDK 步骤为 2，但实际模型请求尝试为 3：第一次请求产生工具调用，第二个步骤经历一次失败及一次成功重试。SDK 步骤数与实际 HTTP 请求数不同；本项目的 `countedFetch` 在每次 HTTP 调用前预留共享预算，所以失败尝试和重试都计数。

## 代码位置

- `vercel_agent/agent.ts`：`run()` 支持单轮 `maxRetries`，默认仍为 0；`ToolLoopAgent` 使用该配置。
- `countedFetch`：每次重试重新检查共享预算；预留失败时记录 `fatal`，确保 SDK 将错误包装成重试失败后，应用仍能报告原预算原因。
- `vercel_agent/tests/loop.test.ts`：新增四项测试，覆盖上述四个场景。

开启方式：

```ts
const result = await agent.run(messages, { maxRetries: 1 });
```

这是 SDK 内部针对当前模型请求的重试。工具执行在这个重试范围之外；不是在外面捕获整个 `run()` 的失败后再次调用 `run()`。

当前 CLI 与对比脚本保持 0 次重试，先前两版对比的配置仍然成立。原生重试只处理 SDK 判定为可重试的错误，不能把该验证结论推广到所有取消、超时或工具执行失败。

测试中的 HTTP 503 带 `retry-after-ms: 0`，减少离线测试等待时间；正常服务的等待策略仍由 SDK 决定。模拟最终回答只用于验证执行流程，不作为真实模型准确性的证据。
