# 累计上下文自动压缩：实现与验证

2026-10-08。SDK Loop 和 Harness 已启用；Python 手写 Loop 尚未启用。没有新增 Agent 框架、搜索服务或密钥。

## 这次解决什么

触发条件是下一次实际模型请求的累计输入容量，包括指令、工具描述和消息，并预留回答空间。它不使用累计计费 token 总数，也不等同于 `read_webpage.truncated`。

原日常记录中两篇网页的 `truncated=true` 来自 10000 字符的有界预览，`output_truncated=false`；并没有证据表明那次模型输入窗口溢出。网页裁切前的提取文本已经保存在快照，仍可按 ID 回查。保留预览限制和诚实覆盖提示，避免把未读部分说成读过。

## 代码与流程

| 文件 | 作用 |
| --- | --- |
| `vercel_agent/context.ts` | 容量估算、摘要指令、来源索引、压缩历史结构 |
| `vercel_agent/agent.ts` | `prepareStep` 检查容量、调用无工具摘要模型、成功提交压缩历史 |
| `vercel_agent/tool_bridge.py` | 压缩前确认还有摘要与继续执行各一次的预算；实际请求仍统一计数 |
| `vercel_agent/cli.ts`、`harness_cli.ts`、`harness.ts` | 即时显示压缩通知，在运行记录保留统计 |
| `vercel_agent/tests/context.test.ts` | 真实 SDK、真实 Python 桥接与快照，模拟模型 HTTP 响应验证各条路径 |
| `vercel_agent/verify_context.ts` | 真实网页和真实模型验证，单独存档 |

流程：下一步请求 → 估算累计输入 → 达到阈值 → 检查预算 → 通知 → 生成工作摘要 → 确认摘要完整且足够小 → 替换已完成的历史 → 继续模型请求。未达到阈值不增加请求。

默认阈值 10000，目标 6500，本地安全输入上限 64000；基于 UTF-8 字节数的保守估算，不是 DeepSeek 精确 tokenizer，也不是模型窗口规格。摘要最多输出 1024 tokens，正常回答仍为 512。配置见 `DEFAULT_CONTEXT_POLICY`，可通过 `Configuration.context_policy` 覆盖。

系统/Skill 指令和最新用户请求完整保留；历史约束、事实、待办依靠有损摘要承接。网页 ID、来源、格式、阅读区间由代码保留；计算等小结果原样留在索引，搜索保留标题和 URL，摘要可能省略。大型非网页结果细节留在运行 trace，不承诺都具备快照回查能力。原始工具返回仍保留在 trace，自动引文验收不会用摘要替代原文。

完成的 tool-call/result 成组移除，避免孤立 ID。消息顺序为系统消息、当前任务、工作摘要，表达已经执行到哪一步，避免把任务放在进度记录之后造成重新开始的歧义。成功后下一轮沿用压缩历史；失败时不改动原成功历史。压缩摘要截断、HTTP 失败、预算不足、固定指令/任务过大或未缩到目标时停止，不靠静默删掉任务恢复。

压缩调用标记为 `vercel_context_compaction`，计入同一份 5 次外层模型、8 次总模型请求和时间预算，实际 tokens 进入总用量。与回答输出上限后的 `vercel_compact_retry` 分开。`context_compactions` 记录输入/输出估算，`context_policy` 记录本次配置，`notices` 保留通知。

实现使用 [AI SDK 的 prepareStep 消息替换接口](https://ai-sdk.dev/docs/agents/loop-control)。SDK 提供循环中的挂钩，摘要和预算策略由本项目实现。

## 离线验证

全部 38 项 TypeScript 测试、54 项 Python 测试通过，类型检查和 `git diff --check` 通过。本次新增 9 项压缩验证：

- 压缩后通过真实 `read_saved_webpage` 回查被摘要遗漏的数值，原读取工具只执行一次，下一轮沿用压缩历史。
- 短上下文不压缩、不增加模型请求。
- 摘要截断时停止，不提交残缺历史。
- 模型预算不够摘要加续跑两次时，不发送摘要请求。
- 摘要 HTTP 503 时停止；即使主循环允许重试，摘要仍不自动重试。
- 摘要未缩小到目标容量时停止。
- 必须保留的用户输入过大时明确停止。
- 上下文压缩与回答输出精简恢复可以共存，不恢复长正文，不重跑工具。
- 两次连续压缩保留旧来源索引和 Skill 指令；两次摘要都占共享预算。

## 真实验证及发现的问题

任务：读取 Anthropic 的 Managed Agents 与 Effective context engineering 两篇博客正文，各用两句话说明对最小 Agent 的借鉴，附实际来源并说明覆盖范围。完整记录保存在忽略的 `reports/context-compaction-runs/`，失败记录未删除。

| 记录目录 | 模型请求 | 工具调用 | 总计费 tokens | 压缩估算 | 结果 |
| --- | --- | --- | --- | --- | --- |
| `context-Q3a0Bq` | 5 | 4 | 19128 | 13966 → 4624 | 压缩和快照回查跑通，输出精简恢复一次；回答错误声称读完全文 |
| `context-Nnog3R` | 5 | 6 | 19352 | 14108 → 5091；16145 → 5783 | 两次压缩后反复下载同一网页，预算停止，未交付答案 |
| `context-fhZKrD` | 3 | 2 | 10256 | **14192 → 5266** | 最新排列与指令下，两篇各下载一次，压缩后直接给出答案，没有输出截断 |

第一轮对第二篇只回读 `[18000,21559)`，中间 `[10000,18000)` 没有回读，答案却说“全文已读”。补充约束：`has_more=false` 只说明本次读到末尾，不说明此前区间已读；首次有界预览可能拼接脚注，不能按长度断言连续区间。现有验收器仍未自动判断完整阅读覆盖，提示词不能保证未来不再发生此类错误。

第二轮的反复下载暴露了压缩后进度表达的歧义。把当前任务放在摘要之后容易看起来像用户重新发起任务，因此调整顺序，并明确不要因正文被压缩而重下同一网页；补读使用文档 ID。不能凭一次前后实测排除采样差异，最新结果仅证明调整后的路径能在此任务跑通，不能保证模型从此不会重复选择工具。

最新轮模型请求分别为普通请求 1666 tokens、摘要请求 5452 tokens、普通回答请求 3138 tokens，合计 10256。两篇各成功读取一次，保留两个快照 ID，无重复下载。答案明确说明“截断的有界预览”“无法声称读完”，未把自动压缩解释成完整阅读。概括的 session/harness/sandbox 解耦、外置恢复状态、最小高信号上下文、清晰工具与适当抽象高度均来自实际读到的内容；不据此认定文章后半也已覆盖。

压缩前后约 63% 的估算输入缩减，不是计费成本节省百分比；摘要本身产生费用。

## 运行

在项目 `vercel_agent` 目录：

```sh
npm run chat
npm run harness -- webpage-reader "读取指定网页，回答问题并标明覆盖范围"
npm run verify:context
```

最后一条会使用真实模型和网页，产生用量，每次保存新目录。普通 CLI 最近记录仍为 `reports/vercel-last-run.json`，验证不会覆盖它。网页预览的 `truncated` 仍可能为 true，表示需要按任务回查，而不是压缩失败。
